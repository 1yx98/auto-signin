# 补丁包 —— 可插拔修复模块

> 建于 2026-09-16。设计目标：**不改主程序，就能装载修复；出问题能整包拆掉，回到装载前的原样。**

## 为什么要有这个东西

主程序 `signin.py` 已经跑了很久、很稳，任何直接改动都有"改坏"的风险。
而修复（比如"滚动循环不等页面变化"）又确实需要改那段代码。

补丁包解决这个矛盾：

- **不装就不生效** —— 主程序一个字节都不动，补丁只安静地躺在 `补丁包/` 里；
- **装了能拆干净** —— 拆卸后 `signin.py` 与安装前**逐字节相同**（用 sha256 证明，不是"应该没问题"）；
- **装错了会自己拦住** —— 锚点不符 / 改错位置 / 引入语法错误，一律拒绝落盘。

## 怎么用（双击 bat 就行）

| 脚本 | 作用 |
|---|---|
| `1_查看补丁状态.bat` | 看每个补丁是"已装/未装/可装/装不上" |
| `2_安装补丁.bat` | 装补丁，装完自动跑一遍测试套件 |
| `3_拆卸补丁.bat` | 还原 `signin.py` 到打补丁前，并校验 |
| `4_列出所有补丁.bat` | 看有哪些补丁、各是干什么的 |

也可以用命令行（在 `补丁包` 目录下）：

```
..\runtime\python.exe patch_engine.py check     # 校验
..\runtime\python.exe patch_engine.py apply     # 全部安装
..\runtime\python.exe patch_engine.py apply P1b # 只装 P1b
..\runtime\python.exe patch_engine.py revert    # 全部拆卸
..\runtime\python.exe patch_engine.py verify    # 确认补丁真的在
```

## 如果装上去发现问题怎么办

```
3_拆卸补丁.bat
```

跑一下，`signin.py` 就回到打补丁前的样子（sha256 会当场打印出来对照）。
你可以慢慢改补丁定义，改完再装回去。**这就是"拆下来完善、继续装上去用"的完整闭环。**

如果拆卸后想手工确认是否真的还原了，看输出的这行：

```
已全部拆卸，signin.py 恢复为基线（sha256=af3865177324d8a5...）
```

## 补丁引擎的三道护栏

引擎的设计原则是 **"宁可装不上，不可装错"**。每次安装都要过三关：

1. **锚点定位（AST）** —— 用 Python 语法树拿到函数/循环的**真实行列号**，
   不做字符串搜索（字符串会搜到注释和文档字符串里的假锚点，本项目踩过三次）。
   定位不唯一（同名函数/多个候选循环）就报错，绝不猜。
2. **落盘前双校验** —— 替换后必须 ① 语法仍正确（`ast.parse`）
   ② 改动行数等于预期（超出就说明改到了别处）。
3. **落盘后签名校验** —— 新代码里必须能找到补丁声明的特征串；找不到即视为失败。

另外还有一条 **幂等保护**：如果特征串已经全部存在，判定为"装过了"，拒绝重复套用。
（这是被负向测试抓出来的真 bug —— 早期版本重复安装会把补丁叠成两层。）

## 关于"断言必须做负向测试"

本补丁包的护栏本身也做了负向测试（`7/7 REAL`）：

| 用例 | 期望 | 结果 |
|---|---|---|
| ① 特征串改成不存在的字符串 | 拒绝 | ✅ 拒绝 |
| ② `expected_delta_lines` 改成错误值 | 拒绝 | ✅ 拒绝 |
| ③ 签名串写一个装完也不会有的 | 拒绝 | ✅ 拒绝 |
| ④ `new` 里埋语法错误 | 拒绝 | ✅ 拒绝 |
| ⑤ 函数名改成不存在的 | 拒绝 | ✅ 拒绝 |
| ⑥ **原样定义（正例）** | **放行** | ✅ 放行 |
| ⑦ **记录说"已装"、文件其实干净 → apply 仍能装回去** | **装回去** | ✅ 装回去 |

第 ⑥ 条特别重要：**只验"该拒绝的都拒绝了"是不够的**，
一个"恒拒绝"的假护栏也能让前 5 条全绿。必须有一条正例证明它**在正常情况下会放行**。

### ★ 用例 ⑦：一次真实事故 + 一次假 REAL

**事故**：跑完本目录的自检脚本后，`signin.py` 被 `reset_to_baseline()` 还原成干净基线，
但 `_state.json` 里 `installed` 仍写着"已装"。此时执行 `apply`：

```
[P1a] 已装过，跳过          ← 谎话
[P1b] 已装过，跳过
签名校验失败：P1a 缺特征串 'def _scroll_fingerprint(' ...
```

→ **补丁装不回去了**。根因：`apply`/`list` 只读 `_state.json` 这个**记录**，
没看文件里的**事实**（`sync_state()` 早就写好了，但没人调用）。
**修法**：CLI 分派前统一同步一次，让所有判断落在文件事实上。

**假 REAL**（这条更值得记）：用例 ⑦ 第一版**直接调 `E.sync_state()`**。
按规矩故意改坏 —— 把 CLI 里那行调用整句禁用，结果 ⑦ **照样 PASS**。
因为它验的是"我顺手能调到的那个函数"，**不是用户真正走的那条路**。
改成 `subprocess` 起真 CLI 后，同一个变异立刻让 ⑦ 变 `摆设!!`（7/7 → 6/7）。

**判据**也随之从"入口有没有调 sync"改成**结果事实三件套**：
① 退出码 0 ② 文件里真出现补丁痕迹 ③ 哈希 == 正常安装结果（逐字节装对了）。

> 负向测试还有个前提（本项目铁律 4.7）：**必须先回到干净基线**。
> 否则"补丁已装"这个状态会让幂等保护先行拦截，
> 用例②③④⑤根本没执行到它们要验证的护栏 —— 那是**假 REAL**，比不做还危险。

> ⚠ **跑完自检记得重新 `apply`**（自检会把 `signin.py` 还原成基线）。
> 修了上面那个缺陷之后，忘了也不会有事：下次 `apply` 会自己发现记录与事实不符，
> 先同步再装，不会再静默跳过。

## 已知边界（诚实记录）

- **拆卸会丢弃打补丁期间的其它手工修改**。`revert` 是用基线备份**整体覆盖**，
  不是逐条反向替换（反向替换需要维护还原锚点，主程序一旦被手工改过就错位）。
  所以：**打补丁期间不要手工改 `signin.py`**。
- `_state.json` 是记录，文件里的特征串是事实。两者不一致时引擎以**事实**为准
  （`sync_state()` 会把对不上的记录清掉）。
- 补丁定义里的 `expected_delta_lines` / `loop_signature` 是**与主程序强耦合**的锚点。
  如果以后主程序那段代码被正规改了，补丁会定位失败——
  这是**预期行为**（说明该更新补丁定义了），不是 bug。

## 适用范围（这个方法值得推广）

本模式适用于**任何"主程序稳定但需要局部修复"的场景**，尤其：

- 主程序正在线上跑，不能停、不能冒险；
- 修复内容边界清晰（改某个函数/某段循环）；
- 需要"随时回退"的安全感；
- 想先小范围验证再决定是否合入主干。

反面：不适用于**大范围重构**（补丁定义会碎成几十条，维护成本超过收益）。

### 第 4 步要搬哪些断言（AST 静态断言即可）

1. `_scroll_fingerprint()` 存在，且**取不到时 `return None`**
   —— 不抛异常、不返回 0、不返回空串。
2. ★ **滚动循环里对指纹的每一处比较都只有 `is not None` / `!=`**，
   **绝不参与** `conf` 计算或 `return` 判定。
   这是最要命的一条：指纹一旦能影响判据，"传感器坏了"就会变成"判决错了"。
3. 指纹取不到（`None`）时流程**退化为"照旧多滚几次"**，不得因此判失败。

> 这三条现在由本目录的 `test_patch_engine.py`（7/7 REAL）间接保障。
> **它们必须在删目录之前，以正式断言的形式进 `smoke_test.py`。**
