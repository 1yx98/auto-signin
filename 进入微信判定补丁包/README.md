# 进入微信判定补丁包 —— 可插拔修复 E

> 建于 2026-09-17。修的是「**匹配不到按钮，却谎报"已在主界面"**」这条误判。

## 这个包修的是什么

**原代码**（`step_enter_wechat()` 内）：

```python
c, x, y = match(ENTER_WECHAT_BTN, scales=(...), must_be_in=_bounds, tag="[进入微信]")
logger.info(f"[进入微信] 检测确认页按钮 conf={c:.3f}" ...)
if c >= 0.8:
    ...点击进入...
else:
    logger.info("[进入微信] 已在主界面，无需确认")   # ← 问题在这
```

**缺陷**：`match()` 在「**完全匹配不到**」或「**命中点越界被拒**」时返回 `conf = -1.0`。
而 `-1.0 < 0.8` 会落进 `else` 分支，于是被当成「**没有确认页**」→「**已在主界面**」。

**这两件事完全不同**：

| conf | 含义 |
|---|---|
| `>= 0.8` | 找到了确认页按钮 |
| `0 <= conf < 0.8` | **真的没有**确认页（已在主界面） |
| **`conf < 0`（-1.0）** | **匹配不到 / 命中点越界** —— 什么都不能断言 |

**09-17 21:22 的实测**：日志打了「已在主界面，无需确认」，
而实际现场是**页面停在登录页、窗口 `IsWindowVisible=0`**。
脚本带着这个错误认知一路走到搜索框，连续失败 4 次，
最后报的是「重启微信后未能进入主界面」—— **真实现场（窗口不可见）从未被说出来**。

这正是本项目铁律 **R14「误报正常状态与漏报真故障是同一枚硬币」**：
把"我看不到"说成"没问题"，会训练人忽略告警。

## 怎么修

| id | 做什么 |
|---|---|
| E1 | `conf < 0` 时**不再**打「已在主界面」，而是：<br>① 重新 `activate("微信")` 一次（配合 `僵尸窗口过滤补丁包`，这次能选到正确的窗口）<br>② 明确告警，并把**窗口是否可见**这个事实打出来<br>③ 只有 `0 <= conf < 0.8` 时才说「已在主界面，无需确认」 |

**改动面极小**：只改一行日志与其前的判定，**不改变点击逻辑、不改变流程走向**。
它做的事是「**把真相说出来**」，让后面出问题时能一眼看到原因。

## 已知边界

- 本包**不修复**"窗口不可见"本身 —— 那是 `僵尸窗口过滤补丁包` 的职责。
  本包只负责**不再谎报**，让真相可见。两者是配套的。
- 若窗口确实不可见且没有僵尸可过滤，脚本仍会失败 —— 但会**如实报出**
  「窗口可见=False」，而不是含糊地说"已在主界面"。
