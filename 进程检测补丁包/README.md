# 进程检测补丁包 —— 可插拔修复 P

> 建于 2026-09-17。修的是「**误启动多余微信实例 → 任务栏弹窗**」这条噪音链。

## 这个包修的是什么

**症状**：用户 09-16、09-17 两次报「**任务栏弹窗**」。

**原代码**（`wechat_running()`）：

```python
def wechat_running():
    try:
        r = subprocess.run(["tasklist", "/FI", "IMAGENAME eq Weixin.exe"], ...)
        return "Weixin.exe" in (r.stdout or "")
    except Exception as _e:
        logger.warning("[进程] 检测微信进程失败(按未运行处理，将由 start_wechat 兜底): %s" % _e)
        return False          # ← 问题在这
```

**缺陷：返回值"表达力不足"** —— 三种完全不同的情况被压成同一个 `False`：

| 真实情况 | 应该怎么做 |
|---|---|
| (a) 微信**真的没运行** | 应该启动微信 |
| (b) `tasklist` **超时/卡住** | **不该**贸然启动（微信可能正在运行） |
| (c) `tasklist` **编码/其他异常** | 同上 |

后果：只要检测环节出一点问题，脚本就会**再启动一个微信实例**。
虽然微信是单实例的（第二个实例会把已有窗口显示出来然后自己退出），
但这个过程会在**任务栏制造弹窗噪音**。

这正是本项目铁律 **R10「函数返回值表达力不足是隐蔽缺陷类型」** 的典型：
> 信号：返回 None/False 后调用方只能靠"猜"分支 → 就问"是不是丢掉了信息"。

## 怎么修

| id | 做什么 |
|---|---|
| P1 | 注入 `_tasklist_has(imagename)` —— 返回 `(是否在, 是否成功查到)` **两个值**，把"查到没有"和"没查成"分开 |
| P2 | `wechat_running()` 改成三态处理：<br>· 查成且确实没有 → `False`（交给 `start_wechat` 启动）<br>· 查成且确实有 → `True`<br>· **没查成** → 用"窗口是否存在"交叉验证；**仍不能确定就不启动**，如实告警 |

**★ 关键取舍**：没查成时**保守地不启动**。
因为"多启动一个实例"的代价（弹窗噪音）比"少启动一次"更明显 ——
而且如果真的没运行，后续 `activate()` 会失败并**如实报出来**（失败不会被掩盖）。

## 已知边界

- 本包**不改变**"微信确实没运行时启动它"这条正常路径。
- 它只影响**检测失败**这一条原本就有缺陷的分支 —— 改动面很小。
- `tasklist` 仍是唯一的一手判据；"窗口是否存在"只是交叉验证
  （注意：僵尸窗口也算"有窗口"，但这里只关心"要不要启动"，保守不启动更安全）。
