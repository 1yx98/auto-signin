## 0. 项目起源与定位

### 0.1 三分钟速览

| 项 | 内容 |
|---|---|
| **它是什么** | 微信 PC 端「油学通」小程序的每日自动签到脚本（Windows） |
| **给谁用** | 西安石油大学学生，本人自用（**个人自用已成熟**） |
| **核心文件** | `signin.py`（约 3985 行，单文件主程序）+ 便携 `runtime/` Python |
| **核心特性** | **"拷贝即用"** —— 整个目录拷到别的电脑就能跑，不需要装 Python |
| **调度** | Windows 计划任务，每日 20:55 触发 |
| **业务时间** | 学校每天 **20:50** 推送晚点名，配置时间窗 `20:50-21:30` |
| **是否关机** | **不关机**（`config.json` 的 `shutdown_after_success: false`） |
| **测试** | `smoke_test.py`，**当前 158 项，全过方可提交** |
| **修复机制** | **可插拔补丁包**（见第六章），主程序零改动 |
| **当前状态** | 主干干净（sha256 `af386517…`）；补丁 P1a/P1b 已备好，**待今晚跑通后安装** |

### 0.2 为什么要做这个

学校的晚点名需要在微信小程序里手动点：打开微信 → 搜索小程序 → 一路点四级入口
→ 到详情页点「签到」→ 等地图定位 → 点「完成签到」→ 确认。每晚 20:50 推送，
窗口期只有 40 分钟，人在忙就容易漏。

**目标**：把这条固定路径自动化，并且——这一点后来变得比自动化本身更重要——
**"失败要能立刻知道，而不是悄悄地漏签"。**

### 0.3 演进阶段

| 阶段 | 时间 | 主题 | 标志 |
|---|---|---|---|
| ① 能跑通 | ~09-07 | 把链路打通 | 首次成功签到 |
| ② 能稳定 | 09-13 ~ 09-14 | 修 bug、加防护、清遮挡 | 修 10 处 + 窗口尺寸防护 |
| ③ **能信任** | **09-15** | **失败可见性 + 判据重构** | **假成功事故 → 三路取交集** |
| ④ 能维护 | 09-16 | 全面复查 + 真实日志校准 + **可插拔化** | **补丁包机制** |

> **转折点**：09-15 的"假成功"事故（脚本通知说签到成功，实际没签）改变了项目走向。
> 此后所有设计都围绕一条原则：**判成功必须有界面依据，绝不凭想当然。**

## 1. 它是怎么工作的

### 1.1 完整执行链路

```
计划任务 20:55 触发（时间窗 20:50-21:30，窗口外不执行或判 not_time）
   │
   ├─ 0. 清障 · 关掉抢占前台的"屏幕外幽灵弹窗"（如联想电脑管家 lxwp）
   │      ↳ 需管理员权限才能结束这类高权限进程
   │
   ├─ 1. 启动/唤醒微信
   │      ↳ 没开就启动；最小化就还原；停在「进入微信」页就点进去
   │      ↳ 等界面真正渲染完成（微信 4.x 会整块白屏 → 检测 + 重绘/重启）
   │
   ├─ 2. 搜索小程序
   │      ↳ 模板匹配顶部搜索框（不写死坐标）
   │      ↳ 粘贴「油学通」→ 多尺度匹配图标 → 点击
   │      ↳ 先清残留小程序进程，保证从工作台首页进入
   │      ★ 全程绝不按 Esc（微信 4.x 按一次就整块白屏且无法自恢复）
   │
   ├─ 3. 逐级进入（按 config 的 signin_nav_steps）
   │      工作台「日常管理」→「签到消息」→「每日签到」→「进入按钮」
   │      ↳ 每步首屏找不到就小步向下滚动（最多 6 次）
   │
   ├─ 4. 签到详情页判定
   │      ↳ 窗口下半部动态扫描宽幅按钮，排除顶部蓝色标题栏
   │      ↳ 蓝色「签到」= 可签 → 点击
   │      ↳ 灰色「已已结束/已签到」= 不点（详见 §5.3 语义辨析）
   │
   ├─ 5. 地图定位页
   │      ↳ 等定位完成、底部「完成签到」由灰变绿 → 点击
   │      ↳ 弹「签到成功,是否返回?」→ 点「确定」
   │
   └─ 6. 收尾
          ↳ 退出码 0（success）/ 1（fail）/ 3（not_time）
          ↳ 写台账 data/signin_history.csv
          ↳ 推飞书结果卡片（附近 7 天统计）
          ↳ 失败现场存 logs/run_*/（PNG 保真）
```

### 1.2 两条关键设计

**① 全程不写死像素坐标。**
搜索图标用多尺度模板匹配，签到按钮按颜色+形状动态扫描，微信窗口大小不同也能识别。

**② 判成功必须有"界面依据"。**
这是被事故逼出来的铁律，见 §9.1。**绝不凭"我点了所以应该成功了"宣布成功。**

### 1.3 失败可见性（三重机制）

签到脚本最怕的不是"失败"，而是"失败了你不知道"。

| 机制 | 内容 |
|---|---|
| **开跑即通知** | 到点启动推蓝色「开始执行」卡片。只有"开始"没有结果 = 卡住了（900 秒全局超时兜底） |
| **每次结果都推飞书** | 卡片底部附 `📊 近 7 天：成功 N、失败 M；成功率 X%`；全不在时段则显示"均不在签到时段" |
| **连续失败升级告警** | "连续失败 ≥2 天"或"近 7 天失败 ≥3 次" → 标题变红底 **「连续失败！」** + "该检查什么"提示 |

> **设计理由**（§8 R14）：单次失败可能偶然，连续失败才是真出问题。
> 而**噪音会训练人忽略告警** —— 所以"误报正常状态"和"漏报真故障"是同一枚硬币。

### 1.4 本地台账 `data/signin_history.csv`

每次运行结束（**包括异常退出**）追加一行：日期、时间、结果、退出码、星期、耗时、
失败步骤、失败原因码、运行目录、备注。

- UTF-8 BOM，Excel 双击不乱码
- 同一天多次运行只按"当天最好结果"统计一次（重试成功不记成失败）
- **纯追加，从不改写历史行**
- 台账写入失败只打 warning，**绝不影响签到主流程**
- 与 Excel/WPS 的锁冲突有专门对策（见 §4 Q10）

**看统计**：双击 `看签到统计.bat`（或 `runtime\python.exe report.py`）。

### 1.5 三轮重试

第一轮失败 → 第二轮重试 → 第三轮补救。每轮独立建 `logs/run_*` 目录。

### 1.6 日志结构

| 日志 | 内容 | 保留 |
|---|---|---|
| `logs/run_YYYYMMDD_HHMMSS/run.log` + 截图 | 单次运行全过程 | 最近 10 次（`keep_runs` 可调） |
| `logs/signin_当天.log` | 当天所有运行汇总 | **按天保留（排查一级依据）** |
| `logs/task_run.log` | 定时任务输出 | 本次 + 上次两份 |
| `logs/samples/` | 真实界面样本 | 长期 |

> ★ **判断历史成败必须读 `logs/signin_*.log`**，不能只看还在的 `run_*` 目录
> —— 早期截图会被清理，但按天日志仍在。**"证据"和"现场"是两份东西。**

## 2. ★ 飞书推送板块

> **这一章回答一个问题：签到跑完之后，你怎么知道结果？**
>
> 整个板块建立在**另一个独立项目**之上（见我 GitHub 的
> [`1yx98/chaoxing-feishu-morning`](https://github.com/1yx98/chaoxing-feishu-morning)
> ——「校园早安助手」）。**签到系统复用了它的飞书自建应用与机器人凭据**，
> 但**代码完全独立**，两者互不依赖、互不影响。

### 2.1 两个项目的关系（重要，别搞混）

```
┌──────────────────────────────────────────────────────────────┐
│  chaoxing-feishu-morning（超星早安推送）                       │
│  GitHub Actions · 云端跑 · 每天 06:00                          │
│  ├─ src/chaoxing.py      超星课程表                            │
│  ├─ src/weather.py       鄠邑校区天气                          │
│  └─ src/feishu.py        飞书卡片（FeishuSender 类）           │
│                          ↓ 创建了「校园早安助手」自建应用       │
│                            持有 App ID / App Secret / chat_id  │
└──────────────────────────────┬───────────────────────────────┘
                               │  复用同一套凭据（同一个 app、同一个群）
                               ↓
┌──────────────────────────────────────────────────────────────┐
│  D:\签到系统\notify_helper\（签到结果推送）                     │
│  本机跑 · 每晚 20:55 · 纯标准库（urllib，零依赖）               │
│  └─ feishu_notify.py     飞书卡片（函数式 send）               │
└──────────────────────────────────────────────────────────────┘
```

| 维度 | 早安系统 | 签到系统的通知板块 |
|---|---|---|
| **代码位置** | `D:\vs code 工作地址\chaoxing-feishu-morning` | `D:\签到系统\notify_helper\` |
| **GitHub** | `1yx98/chaoxing-feishu-morning` | `1yx98/auto-signin`（本项目） |
| **运行位置** | **云端**（GitHub Actions / Ubuntu） | **本机**（Windows，跟着签到跑） |
| **触发时间** | 每天 **06:00**（UTC 22:00） | 每晚 **20:55** 前后（签到开始/结束） |
| **依赖** | `requests` + `pycryptodome` | **纯标准库，零依赖** |
| **HTTP 实现** | `requests` | `urllib.request` |
| **代码组织** | `FeishuSender` **类**（`_token` 缓存在实例上） | 模块级**函数**（`send()`，无状态） |
| **失败处理** | 抛 `RuntimeError`，由 `main.py` 捕获 | **绝不抛异常**，只返回 `True`/`False` |
| **凭据存放** | **GitHub Secrets**（仓库里没有） | `notify_helper/notify_config.json`（本机，不进 git） |

> **为什么不直接 import 早安系统的 `feishu.py`？**
> ① 它是 `requests` 依赖，而签到系统的核心特性是**"拷贝即用"**（便携 Python，
> 不装任何第三方包）；② 它是**类**且会抛异常，而通知模块必须"任何失败都不影响签到"。
> 所以是**同源不同码** —— 复用凭据与卡片范式，不复用代码。

### 2.2 两条接入通道（自动选择）

`feishu_notify.py` 支持两种方式，**按 `notify_config.json` 里填了哪一种自动选**：

| 通道 | 怎么拿凭据 | 特点 | 当前状态 |
|---|---|---|---|
| **webhook 模式**（推荐） | 飞书群 → 设置 → 群机器人 → 添加机器人 → **自定义机器人** → 复制形如 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxx` 的地址 | 一个 URL 就够，**不用建应用、不用配权限** | 未使用（字段留空） |
| **app 模式** | 填 `app_id` / `app_secret` / `receive_id` / `receive_id_type` | 能力完整，可查 API | ✅ **当前在用** |

> ★ **当前用的是 app 模式** —— 复用早安系统那个「校园早安助手」自建应用、**同一个群**。
> `app_id` / `app_secret` / `receive_id`（群 chat_id）/ `receive_id_type=chat_id` 都已填好。
> **webhook 三个字段留空 → 模块自动选 app。**

**webhook 模式的附加安全设置**（若日后切过去）：

- 机器人开了「**签名校验**」→ 把密钥填到 `webhook_secret`
- 机器人开了「**自定义关键词**」→ 把关键词填到 `webhook_keyword`
  （**标题里会自动带上它，否则飞书会拒收**）

**签名算法**（`_webhook_sign`）：对 `"{timestamp}\n{secret}"` 做 HMAC-SHA256 再 base64。

```python
string_to_sign = "%s\n%s" % (timestamp, secret)
digest = hmac.new(string_to_sign.encode("utf-8"), digestmod=hashlib.sha256).digest()
return base64.b64encode(digest).decode("utf-8")
```

**app 模式的调用链**：

```
app_id + app_secret
   → POST /auth/v3/tenant_access_token/internal     （拿 tenant_access_token）
   → POST /im/v1/messages?receive_id_type=chat_id   （Bearer token 发消息）
```

### 2.3 五条设计原则（写在模块 docstring 里，别改）

| 原则 | 说明 |
|---|---|
| **纯标准库** | 只用 `urllib` / `json` / `hmac` / `ssl`，**不依赖 `requests`，零安装** —— 保住"拷贝即用" |
| **绝不抛异常给主流程** | 任何失败**只返回 `True`/`False`**。通知是旁路，**不能反过来影响签到** |
| **卡片失败自动降级** | 卡片（`interactive`）发失败 → 降级成纯文本（`text`）；**每种各重试一次** |
| **每次结果追加写日志** | 同目录 `last_notify.log`（带时间戳） |
| **凭据只在一处** | 只放 `notify_config.json`，**不进 git、不写日志、不打印** |

### 2.4 卡片分级配色

`_LEVEL_TEMPLATE` 决定卡片头部颜色：

| level | 颜色 | 用于 |
|---|---|---|
| `success` | 🟢 green | 签到成功 |
| `fail` | 🔴 red | 签到失败 / 连续失败升级 |
| `warning` | 🟠 orange | **不在时段（`not_time`）** / 没读到结果 |
| `info` | 🔵 blue | 开始执行 / 连通性测试 |

**标题映射**（`notify_signin_result`）：

| 结果 | 图标 | 标题 | 配色 |
|---|---|---|---|
| `success` | ✅ | 油学通签到成功 | green |
| `not_time` | 🕘 | 油学通签到：不在时段 | orange |
| 其它（fail） | ❌ | 油学通签到失败 | red |
| 读不到结果 | ⚠️ | 油学通签到：没读到结果 | orange |

> ★ **关键**：`not_time` 用 **orange 而不是 red** ——
> 这是 §5.3 那次"语义判断错误"修复在通知层的体现。
> **"今天还没推送"是正常状态，不是失败，不该用红色吓人。**（§8 R14）

### 2.5 ★ 四个推送时机（覆盖全部退出路径）

主程序通过 `signin.py` 里的两个封装函数接入，**四个调用点覆盖所有退出情况**：

| # | 触发场景 | `signin.py` 行 | 走哪个函数 | 推送内容 |
|---|---|---|---|---|
| 1 | **开跑** | `3671` | `notify_start()` | 🟦 "开始执行"（**无后续结果 = 流程卡住**，全局超时兜底） |
| 2 | 屏幕锁定，签到无法开始 | `3686` | `notify_feishu(reason)` | ❌ 提前中断 + 原因 |
| 3 | 微信启动失败 | `3726` | `notify_feishu(reason)` | ❌ 提前中断 + 原因 |
| 4 | **正常收尾** | `3805` | `notify_feishu()` | ✅ / 🕘 / ❌ + 统计（成功、not_time、失败三条路都经过这里） |
| 5 | **脚本抛异常** | `3825` | `notify_feishu(reason)` | ❌ 提前中断 + 异常类型 |

**为什么"开始"和"结果"要分成两个函数**：

> 这条是"开始"、那条是"结果"，**各自独立发**。
> `not_time` 等提前退出情况不会有结果，**最坏就是多一条开始通知，无副作用**。

**两个函数的语义差异**：

| 函数 | 何时用 | 为什么分开 |
|---|---|---|
| `notify_signin_result(run_dir)` | `result.txt` **已写** | 从 `run_dir` 读结果、组稿 |
| `notify_early_exit(reason, ...)` | `result.txt` **还没写** | 直接按 `reason` 组稿 |

> ★ 提前中断是"失败也发"里**最容易被静默漏掉的一类** —— **尤其锁屏**。

### 2.6 ★ 幂等保护（`_FEISHU_DONE`）

```python
_FEISHU_DONE = [False]

def notify_feishu(reason=None):
    if _FEISHU_DONE[0]:
        return                      # ← 一次运行只推一条
    _FEISHU_DONE[0] = True
    ...
```

**为什么需要**：异常路径可能让同一次运行走到多个调用点
（比如"脚本抛异常"后 `finally` 又想推结果）→ **同一次运行会推两遍**。

> **用列表 `[False]` 而不是全局布尔**：闭包/嵌套作用域下要可变对象才能改到外层。
>
> ⚠️ **注意（诚实记录）**：`_FEISHU_DONE` 的兜底作用**在强杀场景下保护率接近 0%**
> —— 进程被 `taskkill /F` 直接终止，`finally` 都不会执行。
> 真正的强杀兜底是 §4 Q6 的**残留标记**（下次启动代为报告）。

### 2.7 `read_run_summary()`：从运行目录读出结构化结果

推送内容不是"猜"的，是**从磁盘上的事实读出来的**：

| 来源 | 读什么 |
|---|---|
| `run_dir/result.txt` | 结果 / 退出码 / 含义 / 耗时 / 时间 / 时间线 |
| `run_dir/step_trace.json` | 失败步骤（`fail_step`）/ 失败原因码（`fail_code`） |
| `run_dir/FAIL_*.png` | 失败现场截图名（**只列前 3 张**） |

**推送卡片的构成**：

```

─────────────────────────────
✅ **签到成功**                       ← meaning

失败步骤：`NAV_ENTRY_FAIL`（…）       ← 仅在失败时
现场截图：FAIL_xxx.png                ← 仅在有失败截图时
目录：`run_20260916_205512`
📊 近 7 天：连续成功 3 天…            ← history.stats(7) 的 streak_desc
⚠️ **需要人工检查**：…                ← 仅在升级告警时
```

### 2.8 统计与升级告警

**统计行**（`history.stats(7)`）：

- 读 `data/signin_history.csv` 台账，附一句"近 7 天"统计
- **台账为空时不显示** —— 否则"成功 0、失败 0"看着像出问题了
- 导入失败或统计异常 → **降级为不显示，绝不阻断通知**

**升级告警**（`should_escalate()`）：

| 条件 | 行为 |
|---|---|
| **连续失败 ≥2 天** 或 **近 7 天失败 ≥3 次** | 标题变 **「连续失败！」**，配色改 red，附"该检查什么"提示 |

**两个关键约束**：

1. **只在"本次也失败"时升级** —— **成功不会被历史拖累成红色**
2. **读不到台账就返回 `False`** —— **宁可少告警，也不能因为统计模块出问题就误报**

**升级时的提示文案**（告诉用户该查什么）：

> ⚠️ **需要人工检查**：设置「离开后要求登录」是否放宽、WiFi 是否连接、微信是否已登录

### Q6 `atexit` 中断兜底在强杀下完全不执行 ★★（P0-1）

| 项 | 内容 |
|---|---|
| **现象** | 脚本被强杀后，"结果未知"的告警一条都收不到 |
| **实测结论** | 见下表 |
| **修复** | **三层兜底**：atexit + signal + **残留标记（主保障）** |
| **验证** | 真实强杀实测 + 6 场景 + 3 分支；测试 109 → 114 项，连跑 6 次一致 |

**实测证据（决定方案的关键实验）**：

```
正常退出     -> atexit 执行
terminate()  -> atexit 不执行
taskkill /F  -> atexit 不执行（内核级终止，进程没有任何执行机会）
```

**"用户掐脚本"的现实路径**（关窗口 / 任务管理器结束任务 / 计划任务 30 分钟强杀）
**全落在后两条** → 只靠 atexit 的兜底**保护率接近 0%**。

**三层分工**：

| 层 | 覆盖场景 | 特点 |
|---|---|---|
| ① `atexit` | 正常退出 | 保留（无害），但正常退出本就发过通知，实际用不上 |
| ② `signal.SIGINT/SIGTERM` | Ctrl+C / 关窗口 / `terminate()` | **当场**发提醒，时效最好 |
| ③ **残留标记（主保障）** | **`taskkill /F` / 计划任务强杀** | **唯一能覆盖全部场景**，下次启动代为报告 |

**为什么要 ③**：`signal` 能覆盖 Ctrl+C 和 `terminate()`，但 `taskkill /F`
是内核级终止，**进程收不到任何信号**。而计划任务超时强杀
（`install_task.ps1` 设了 `ExecutionTimeLimit = 30 分钟`）走的正是这条路。

**③ 的关键设计（改动时别破坏）**：

- 路径 `.agent/_in_progress.json`
- **只在首次点击"完成签到"之后落盘** —— 这是"值得告警"的门槛。
  还没点过签到的中断没有信息量（下次正常跑就行），不该制造噪音
- **原子写盘**（临时文件 + `os.replace`）
- `main()` **开头**（在 `notify_start()` 之前）检查残留 → 补发 → 立即清除
- 标记损坏 / 缺 `run_dir` → 删除并按"无残留"处理（避免坏标记永久卡住每次启动）
- 提醒带：上次开始时间、运行目录、**现场截图名**
- signal 处理里用 **`os._exit(1)`** 而非 `sys.exit`（`SystemExit` 会被主循环吞掉）

### Q9 白屏判定混淆"测不了"（P1-1）

### 5.3 ★ 事故三：把「已结束」判 fail —— 语义判断错误（09-16）

这是**最值得细读的一节**，因为它完整展示了"我猜错 → 日志纠正"的过程。

#### 4.3.1 我原来的理解（错的）

「已结束」= 今天已经签过了 → 判 fail 合理，只是识别率要提升。

#### 4.3.2 用户的真实语义（2026-09-16 傍晚澄清）

> 用户每天 **20:50** 才收到学校的晚点名推送。
> 在推送到来**之前**打开详情页，看到的是**昨天那条记录的「已结束」**。
> 「已结束」= **今天的还没推送，这是昨天的残留** ——
> 它是**正常状态，不是失败**。

**所以脚本把「已结束」判成 `fail` + 退出码 1 + 留失败现场 + 发飞书告警，
是彻底的误报。** 这不是识别率问题，是**语义判断错误**。

> ★ 副作用极坏：每天晚上都会产生一次无意义的失败告警 + 自愈失败计数 +
> 一堆失败现场目录。**噪音会训练人忽略告警**，最后连真故障一起忽略。

#### 4.3.3 真根因：证据在导航层被丢弃

**我最初的错误猜测**：以为是时间守卫（`before_signin_start`/`_within_signin_window`）没生效。

**日志给出的铁证** —— `logs/signin_20260916.log` 16:34:03，三行紧挨着：

```
16:34:03 [INFO]    [已签到判据] 几何 + 字迹双路一致 → 字迹符合「已签到」(底色204/对比25/墨迹0.0239/亮字)
16:34:03 [WARNING] [OCR] 详情页按钮文字=「已结束」含否定词「已结束」→ **否决**'已签到'判定
16:34:03 [ERROR]   [导航] 第4步「每日签到里的进入按钮」滚动后仍未找到，终止      ← 证据到这里就消失了
```

**这三行属于 `open_signin_entry()`（导航函数），不是 `click_sign_button()`（详情页判据）。**

**缺陷链**：

```
OCR 明确读出「已结束」
  → ocr_veto_signed 返回 False
  → signed_detail_button 里 continue，最终 return None
     ★ 问题在这：函数只有"按钮dict / None"两种返回，
       无法区分 (a) 没有符合几何的灰块 (b) 几何像但字迹不像 (c) OCR 读到「已结束」
       三者对调用方**长得一模一样**
  → open_signin_entry 把 (c) 当成"没找到入口"
  → logger.error("滚动后仍未找到，终止") → return False
  → attempt_once: TRACE.end_step("fail", "NAV_ENTRY_FAIL") → return "fail"
  → 误报失败 + 留现场 + 发告警 + 记自愈失败
```

> **一句话概括**：OCR 好不容易认出了最关键的那条证据，
> **却在导航层被当成"匹配失败"扔掉了**，决策层只看到"导航失败"。

#### 4.3.4 修复：可选 `out` 出参

给 `signed_detail_button` 加**可选 `out` 出参**，把"读到否定词"这个事实带出去：

1. `signed_detail_button(..., out=None)` —— `out is None` 时**行为与改动前完全一致**
   （刻意做成可选出参而非改返回值：**返回值语义被多处依赖**，
   改它等于让所有调用点重做判断，风险远大于收益）
2. OCR 否决分支内写 `out["negative"] = True`
   （**只在真正走到 OCR 否决那一个按钮时写**，几何/字迹不符不算）
3. `open_signin_entry` 传 `out=_out`，读 `_out.get("negative")` → `return "not_time"`
   （沿既有链路 → 退出码 3、不告警、不留失败现场、不记自愈失败）

> **关键认知**：这条 `not_time` 链路**本来就存在且正确**，
> 缺陷只是**"事实到不了它那里"**。修复不是新建链路，而是**把丢掉的证据接回去**。

#### 4.3.5 验证（真实验证 + 负向测试）

- **用户手跑 17:58 + 18:14 两次**：`最终结果=not_time 退出码=3`、
  `[自愈] 非签到时段，不更新故障状态`、**无 `FAIL_*.png`** ✅
- **负向测试 4 项全部 REAL**
- 三层回归断言 `test_ended_record_propagates_not_time`

#### 4.3.6 本章的方法论收获

1. **真实日志能推翻"很有道理的静态推断"，且推翻得不留情面。**
   前九章全部建立在静态推断上，第十章的真实日志直接推翻了我两个结论。
2. **函数返回值的"表达力不足"是一种隐蔽的缺陷类型。**（§8 R10）
3. **区分"正常状态"与"故障"是产品的核心职责，不是细节。**（§8 R14）

### 7.4 ★ 三道护栏（原则：**宁可装不上，不可装错**）

每次安装都要过三关：

| 关 | 内容 | 为什么 |
|---|---|---|
| **① 锚点定位（AST）** | 用 Python 语法树拿函数/循环的**真实行列号** | 不做字符串搜索 —— 字符串会搜到**注释和文档字符串里的假锚点**，本项目踩过**三次**。定位不唯一就报错，**绝不猜** |
| **② 落盘前双校验** | ① 替换后语法仍正确（`ast.parse`）<br>② 改动行数**精确等于** `expected_delta_lines` | 超出就说明**改到了别处** |
| **③ 落盘后签名校验** | 新代码里必须能找到补丁声明的 `signatures` 特征串 | 找不到即视为失败 |

外加**幂等保护**：特征串已全在 → 判"装过了"，**拒绝重复套用**。

#### 7.7.1 ★ 用例 ⑦ 的来历：一次真实事故 + 一次假 REAL

**事故**（2026-09-16 实测后）：

跑完 `test_patch_engine.py` 自检脚本 → 它把自己注入的变异都还原了，
但**顺手把 `signin.py` 也还原成了干净基线**（`reset_to_baseline()`），
而 `_state.json` 的 `installed` 里**仍写着"已装"**。接着用户执行 `apply`：

```
[P1a] 已装过，跳过          ← 谎话，文件里根本没有
[P1b] 已装过，跳过
签名校验失败：P1a 缺特征串 'def _scroll_fingerprint(' ...
```

→ **补丁装不回去了**，而且那句"已装过"完全误导。

**根因**：`apply` / `list` 只读 `_state.json` 这个**记录**，没看文件里的**事实**。
引擎里其实早就有 `sync_state()`（注释里明写"记录服从事实"），**但没人调用它**。

**修法**：CLI 分派前统一 `_sync_state_quiet()` 同步一次，
让所有判断落在文件事实上。修完输出变成：

```
[状态同步] 记录与文件不一致，已按文件事实修正：
    P1a: 文件里已无签名痕迹，从'已装'记录中移除
[P1a] 已安装：……（改动 +30 行）
2 个补丁签名校验全部通过
```

**★ 假 REAL**（这次差点又栽）：

用例 ⑦ 第一版写的是**直接调 `E.sync_state()`**。做完之后按铁律故意改坏 ——
把 CLI 里那行 `sync_msgs = _sync_state_quiet()` 整句禁用，结果 ⑦ **照样 PASS**。

原因：它验的是"我顺手能调到的那个函数"，而**不是用户真正走的那条路**（`apply` 子进程）。
→ 改成 `subprocess.run([python, patch_engine.py, "apply"])` 起真 CLI 后，
同一个变异立刻让 ⑦ 变 `摆设!!`、汇总从 7/7 掉到 **6/7** —— 这才是护栏真的存在的证明。

**判据也一并改掉了**：不再判"有没有调 sync"（那是"入口有没有做某事"），
而是判**结果事实**三件套 ——

### 7.8 引擎开发中踩到的技术坑（真实记录）

**坑 1：顶层 `for` ≠ 要改的 `for`** ★

`open_signin_entry()` 的顶层 `for` 是"遍历导航步骤"的**外层循环（140 行）**，
要改的 `for k in range(6)` **嵌套**在里面。只按顶层索引取会**整个替换外层循环**
→ **行数护栏当场拦下**（实际 -88，预期 +30）。

→ 改用 `signature` 定位 + **嵌套去重（保留最内层）**
（外层片段**包含**内层，必然同时命中）。

```python
innermost = []
for h in hits:
    contains_other = any(other is not h and h.lineno <= other.lineno
                         and other.end_lineno <= h.end_lineno for other in hits)
    if not contains_other:
        innermost.append(h)
```

**坑 2：`expected_delta_lines` 是救命的** —— 它正是拦住坑 1 那次灾难的东西。

**坑 3：`_state.json` 与文件事实可能不一致** → 加 `sync_state()`，**以文件为准**。

**坑 4：重复安装会把补丁叠成两层**（★ 由负向测试抓出的**真 bug**）

用例 ⑥（正例）意外被拒，报 `实际 +44，预期 +28` ——
因为补丁已装，再次套用会把新循环**再包一层**替换。
→ 修复：加**幂等保护**。

**坑 5：假 REAL**（★ 由负向测试抓出的**第二个真 bug**）

加了幂等保护后，用例 ②③④⑤ 全因"特征串已全部存在"被拦截
→ **行数/语法/函数名三道护栏根本没执行到** → 表面 5/6 REAL，实为**假 REAL**。

→ 修复：**负向测试脚本必须内建"每条用例前恢复基线"**（`reset_to_baseline()`），
不能依赖调用者记得先 revert。修正后得到真正的 **6/6 REAL**。

> **这两个 bug 都是负向测试抓的，不是读代码发现的。**
> 这印证了 §8 R3：**负向测试最大的价值是阻止你制造假护栏。**

### 7.11 已知边界（诚实记录）

- **拆卸会丢弃打补丁期间的其它手工修改**。`revert` 是用基线备份**整体覆盖**，
  不是逐条反向替换（反向替换需要维护还原锚点，主程序一旦被手工改过就错位）。
  → **打补丁期间不要手工改 `signin.py`**。
- `_state.json` 是记录，文件里的特征串是事实。两者不一致时引擎**以事实为准**
  （CLI 每条命令开跑前会自动同步一次，见 §7.7.1）。
- **`test_patch_engine.py` 跑完会把 `signin.py` 还原成干净基线** ——
  这是它 `reset_to_baseline()` 的设计（每条用例必须从干净基线出发，否则是假 REAL）。
  → **跑完自检必须重新 `apply`**。别忘了。修了 sync 之后这件事至少不会再
  "静默装不回去"，而是会明确告诉你"从'已装'记录中移除"再装一遍。
- 补丁定义里的 `expected_delta_lines` / `loop_signature` 是**与主程序强耦合**的锚点。
  如果以后主程序那段代码被正规改了，补丁会**定位失败** ——
  这是**预期行为**（说明该更新补丁定义了），**不是 bug**。
- **`_scroll_fingerprint` 的采样时机偏早**：实测两轮（09-16 19:01 / 20:55）
  每轮都输出 `页面未变化，继续滚动(1/3)`，**从没到过 `(2/3)`/`(3/3)`**。

### 7.13 第二个补丁包：`跳过无效滚动补丁包`（P2a+P2b）

> 建于 2026-09-16 21:25。用户要求"名字就是功能加'补丁包'"，故目录名

#### 修什么

已签到态下第 4 步滚 6 轮必然全失败（蓝按钮不存在），白耗约 42 秒（见 §7.11）。
P2 在**滚之前先探一下**：若详情页已是「已签到/已结束」态 → 直接 break，
落入下方**本来就有、本来就正确**的 `if not found:` 兜底分支。

| id | 做什么 | 风险 |
|---|---|---|
| P2a | 注入 `_already_signed_detail()` 预检函数 | 极低（纯新增，不被调用时无影响） |
| P2b | 滚动循环前预检，命中则跳过 6 轮 | 低（**探不到就完全退化为原行为**） |

**为什么不会引入误判**：探测函数返回 `False` 时，流程与打补丁前**逐字节等价**。
即它**没有能力**把"该成功"变成"失败"——只会更快，不会更错。

#### ★★ 跨包冲突保护（一次真实事故的产物）

**事故**：21:26 执行 `补丁包/patch_engine.py revert`（本意只拆 P1），
输出"已全部拆卸，signin.py 恢复为基线"，**把 P2a+P2b 一起抹掉了**——
而 P2 包的 `_state.json` 仍显示"已装"。

**根因**：整包拆卸 = 用**自己的**基线整体覆盖。`补丁包` 的基线是原版，
覆盖回去当然把后装的 P2 冲掉。当时的"跨包防护"只查注册表，
而注册表机制**还没上线**，`补丁包` 从没登记过 → 它以为"没冲突" → 放行。

**修法（两道判据，且判据 1 的方向被修正过两次）**：

| 判据 | 问的问题 | 拦住的情况 |
|---|---|---|
| ① 注册表交叉核对 | **有没有别的包登记的最后 sha 正好等于当前文件 sha？** | 别人**写在我之后**（危险） |
| ② 本包自查 | **我上次改完登记的那个 sha，还是当前 sha 吗？** | 有人在我之后动过文件（含本包从未登记过的旧场景） |

**① 的方向曾写反**（`sha256_after != cur` 视为冲突），后果是：
- 别人写在我**之前**（无害）→ 被**误报**冲突；
- 别人写在我**之后**（有害）→ 反而**漏报**。

实测踩到的是误报那一面：P2 包**自己**的 `revert P2b` 被自己的防护拦住，
而引擎提示还叫人"改用 `revert <单个补丁id>` 逐条拆"——**那条路同样被拦，建议自相矛盾**。
修正为"**谁的登记 sha == 当前 sha，谁就是最后落笔的人**"，与判据 ② 一致。

**原则**：**宁可拆不掉，不可拆错。**

#### ★ 拆卸姿势（因跨包而特殊）

本包基线 = **"已装 P1 的版本"**（`2f2d675c…`），所以：

- **本包不能整包拆**（整包覆盖会把 P1 一起带走，但 P1 的基线是原版、能自己拆干净）；
- 正确姿势是**逐条拆**：
  ```
  runtime\python.exe 跳过无效滚动补丁包\patch_engine.py revert P2b
  runtime\python.exe 跳过无效滚动补丁包\patch_engine.py revert P2a
  ```
  → 文件回到 `2f2d675c…`（= 只装 P1）。
- 要**彻底回原版**：先拆本包两条 → 再 `补丁包/patch_engine.py revert` → `af386517…`。
  **顺序不能颠倒**（先拆 `补丁包` 会被判据 ② 拦住，这是设计）。

#### `sync_state()` 修正为**双向**

原来只做"文件里没痕迹 → 删掉假记录"这一半。
反过来（**记录说没装、文件里其实装着**）没处理，后果：
另一个包在本包之后落笔 → 本包记录被冲成空，但文件里补丁明明还在
→ `list` 打印"已装 0 个"——**记录压过事实**，人看了以为没装。
现改为双向对齐，并把这件事固化成负向测试用例 ⑨。

### 7.14 三个新补丁包（2026-09-17 晚）：僵尸窗口 / 进程检测 / 进入微信判定

> 起因：09-17 晚定时任务**没签上**，且用户手跑两次**又出现任务栏弹窗**。

#### 7.14.1 根因：僵尸窗口（zombie window）

**微信退出后，它的顶层窗口对象会在系统里残留** —— 可以枚举、`GetWindowRect`
仍返回有效坐标（看起来完全正常），但 `IsWindowVisible` 恒为 0，
且**任何激活手段都无效**（进程已死，没人处理窗口消息）。

```
微信退出 → 主界面窗口（1118x1715）残留为僵尸
  → find_wins("微信") 找到它（rect 大，按面积排序排第一）
  → activate() 选中它 → ShowWindow/SetForegroundWindow 全无效
  → 真正可用的窗口（登录页 586x773）从未被激活 → 点击落空
  → 搜索框匹配失败 → 重启微信 → 僵尸仍在列表 → 死循环
  → 用户看到「任务栏反复弹窗」
```

**★ 实测铁证（两个窗口尺寸完全不同，证明是两个窗口）**：

| | 脚本看到的 | 真实可用的 |
|---|---|---|
| hwnd | 393430 | 655858 |
| rect | (879,0,1997,1715) | **(1147,472,1733,1245)** |
| 尺寸 | 1118x1715（**已登录时的主界面尺寸**） | **586x773（未登录时的登录页尺寸）** |
| 状态 | `Visible=0`（僵尸） | `Visible=1` |

> 586x773 正是 §7.5 里记的 09-07~09-15 那 8 次成功运行的窗口尺寸。
> **另一个证据**：日志 21:23:02 出现 `[进程] 微信未运行，启动: ...`
> —— `wechat_running()`（查进程）说"不在"，而 `find_wins()`（枚举窗口）说"在"。
> **两个函数看到的事实矛盾，但都正确**：进程死了，窗口对象还残留。

#### 7.14.2 三个包各修什么

| 包 | 补丁 | 修什么 |
|---|---|---|
| **`僵尸窗口过滤补丁包`** | Z1/Z2 | 注入 `_win_is_zombie()`（`OpenProcess` + `GetExitCodeProcess != STILL_ACTIVE`），并在 `find_wins()` **进候选列表之前**过滤僵尸窗口 |
| **`进程检测补丁包`** | P1/P2 | `wechat_running()` 原来把「真没运行」「tasklist 超时」「编码异常」**压成同一个 False**（铁律 R10 的典型）；改成三态，**没查成时不贸然启动**，避免制造多余实例的弹窗噪音 |
| **`进入微信判定补丁包`** | E1 | `match()` 返回 `conf=-1.0`（匹配不到/命中点越界）时**不再谎报「已在主界面」**；明确打出"窗口可见=False"这个事实 |

**★ `_win_is_zombie()` 的安全设计**：**取不到信息时一律按"活着"处理**（返回 False）。
这是铁律 **R7「读不到 ≠ 坏的」** —— 宁可留下一个可疑窗口，
也绝不因为权限问题把正常窗口误判成僵尸而丢掉它。

#### 7.14.3 ★ 引擎新增第 4 种 op：`replace_lines`

原 3 种 op **都改不了函数体内部的语句**：

| op | 局限 |
|---|---|
| `replace_function_head` | 只换 `def` 那一行 |
| `replace_loop` | 只换整个 for 循环 |
| `insert_before_function` | 只能加在函数**外面** |

而这三个修复恰恰都是"改函数体里的一个判断/一行调用"。
实测：修 `find_wins()` 要在 `out.append((h, t))` 前加过滤，三种 op 一个都用不上。

**新 op 的安全设计**（与既有 op 同一标准：宁可装不上，不可装错）：
- 锚点必须在**目标函数体内**（不是整个文件里搜）
- 锚点在该函数内必须**恰好命中 1 行**：0 行 → 报"找不到"；多行 → 报"定位不唯一"
- 按 strip 后**精确相等**比较，不做模糊/子串匹配
- 仍受 `expected_delta_lines` 行数校验

#### 7.14.4 ★★ 又一次假 REAL：多道护栏互相顶替

**变异验证时发现**：把引擎里「锚点找不到 → 拒绝」改成「找不到就退回函数首行」后，
用例①**照样 PASS** —— 因为退回首行产生了**语法错误**，被**语法护栏**拦下了。
表面上"拒绝了"，其实要验的那道护栏已经坏了。

**根因**：引擎有多道护栏（锚点 / 行数 / 语法 / 签名），**它们会互相顶替**，
而原判据只问「拒没拒」，不问「**是谁**拒的」。

**修法**：给测试的 `caser()` 加 `expect_msg` 参数 —— **断言拒绝理由**。
用例① 现在要求拒绝信息里必须含「找不到锚点行」。
加固后重做变异：用例① 正确变 `摆设!!`（8/9）；还原 → 9/9 ✓

## 8. 方法论与经验沉淀（14 条铁律）

> **这一章是项目最贵的资产。** 每条都是踩过坑换来的，不是从书上抄的。
> 其中 R1、R4、R5 是**反复踩过的**，请务必严格执行。

### R1 断言一律 AST，禁用字符串/正则/`in` ★★★

凡"检查代码里有没有做某件事"的断言，**必须用 AST 查真实节点**。

**原因**：注释与文档字符串会命中，且它们**不是 AST 节点**。本项目**已踩 5 次**：

| 次 | 踩法 |
|---|---|
| ① | 判据顺序断言被**注释**里的函数名误导 |
| ② | `_ocr_binarize` 调用断言被**文档字符串**骗过（删掉真调用后断言仍 PASS，是**负向测试**发现的） |
| ③ | `os.replace` 原子写断言写成 `("os.replace" in ast.dump(n)) or ("os.replace" in src[...])` —— **后半段在源码字符串里搜**，必然命中 → **断言恒真成摆设** |
| ④ | `_hidden` 断言被函数体里的**注释**骗到 FAIL（注释写着旧式样，真实代码是对的） |
| ⑤ | 负向测试锚点被注释干扰 |

**规则（刻死，无例外）**：
- 检查**参数是否存在** → `fn.args.args`
- 检查**有没有调用某函数** → `ast.Call`
- 检查**某个赋值表达式** → `ast.Assign` + `ast.get_source_segment`
- `ast.get_source_segment` **可以**（它读的是**真实节点**的片段，不是全文搜字符串）
- **一条断言若有多个子检查，每个子检查都要单独做负向验证**（不许抽查）
  —— 第 ③ 次的漏网正是因为只验了 2 个子检查、漏了第 4 个

> **同一个错犯 5 次 = 规则没执行到位，不是运气问题。**

### R2 `ast.Constant` 里 `None` 也是常量

想拦 `return 1.0` 时写 `isinstance(n.value, ast.Constant)`
会把 `return None` 一起 FAIL。

**必须**：
```python
isinstance(n.value.value, (int, float))
```

### R3 护栏必须"改坏必 FAIL"才算存在 ★★

- **写完立即跑一次**（否则一上线就是红的，**已踩 2 次**）
- **故意改坏它守护的代码，看是否 FAIL**
- **⚠ 不要写"不可能发生的场景"**：我写过"关子 logger propagate → 核对字节数不变"，
  三种改坏**全 PASS**，因为该场景**永远不可能发生**。
  → **一条永远 PASS 的断言比没有断言更坏。**
- **判据要落在"结果/事实"**，不能落在"入口有没有做某事"
- **负向测试最大的价值是阻止你制造假护栏** —— 补丁引擎的两条假护栏都是它抓的，
  不是读代码发现的

### R4 负向测试规范（每轮照做） ★★

1. **先固定干净基线 + 记录 sha256**
   （踩过：`cp signin.py /tmp/bak.py` 在**前一次注入之后**执行，
   → "干净备份"里带着上次的注入内容 → 后续全跑在错误基线上）
2. **按字节读写**（`rb`/`wb` + 显式换行）
   —— 文本模式会**静默**把 CRLF 转 LF
3. 替换串**恰好命中 1 处**，否则 SKIP。**SKIP ≠ 通过**
4. 每条用例**恢复后立即核对 sha256 与基线一致**（防"恢复不干净"）
5. **还原写在 `finally` 里**（踩过：进程被中断，注入被留在 `signin.py` 里）
6. **★ 脚本必须内建"每条用例前恢复基线"**，不能依赖调用者记得先 revert
   （2026-09-16：幂等保护上线后，用例 ②③④⑤ 全因"已装"被拦，
   **根本没执行到要验的护栏** → 表面 5/6 REAL，实为**假 REAL**）
7. **裁决分类**：`REAL` / `DUMMY`（改坏仍 PASS，摆设）/ `BLIND` / `SKIP` / `RESTORE_FAIL`
8. 所有子项**逐个**验证，**不抽查**

### R5 别把"我的观测"当成"事实本身" ★★★（翻车最多）

| 子条 | 踩坑经过 |
|---|---|
| **注释不是证据** | 发现两处注释与实际相反（都是猜的）。**截图 + 实测数字才是证据。** |
| **扫描工具输出不能直接当结论** | 复审 `install_task.ps1` 时，我的扫描脚本用 `utf-16` 解码，输出被截断 → "发现"它缺 `-ExecutionTimeLimit`，**差点把一条不存在的缺陷写进报告并动手"修复"**。读原文件才发现两处防护都在。→ **跨编码读文件时，必须先确认解出的字符串长度/结尾是合理的。** |
| **比较两个数字前，先确认"前提是否相同"** | 排查 12:33 故障时，我拿 `559×2=1118` 推断"DPI 200% 缩放导致坐标错位"，还找了历史日志"佐证"，差点据此改代码。**实测证伪**。那 559 是我在**一个没调 `_enable_dpi_awareness()` 的临时脚本**里测的；而 1118 是 `signin.py`（设了感知）拿到的。**两个数字前提不同，不可比。** → **临时诊断脚本必须复刻真实脚本的所有前置步骤。** |
| **日志里打印的数字 ≠ 用于决策的数字** | 我把 `[进入微信] conf=0.285` 当成"阈值失效"。读代码才知：`match(must_be_in=...)` 会**罚分压低 conf**，而判定语句仍然是 `if c >= 0.8`。→ **判断阈值是否合理必须看判定语句本身。** |
| **"以前能用" ≠ "以前是对的"** | 旧代码长期用窗口外像素当判据，只是窗口全屏时恰好掩盖；窗口一变窄立刻现形。→ 排查要问：**"它依赖什么隐含前提？这个前提今天变了吗？"** |

> **与前几轮同源**：跨时间对比（拿 12:33 的 rect 比"现在"的 rect）、
> utf-16 解码读到截断内容、"备份被上一次注入污染" ——
> **都是把"我的观测"当"事实本身"。**

### R6 归因：两头都要自查 ★★

**别把"可修的 bug"误判成"能力上限"（最贵的一课）**

真实案例：OCR 识别「已结束」命中率只有 **1.1%**，我判定"这是 OCR 先天弱项，
只能靠时间守卫兜底"。**这个结论是错的** —— 真根因是按钮**对比度只有 51/255**
（白字 255 在浅灰底 204 上），是个**可修的工程 bug**。
加一步 Otsu 二值化后：**8.6% → 40%**，「已签到」**88.6% → 100%**。

> **判断信号**：某特性"表现极差但又不是完全为零"时，先怀疑**输入质量/预处理**，
> 而不是急着归因为工具能力不足。**极低命中率本身就是"有系统性障碍"的异常信号。**

**诚实必须配合追根因**：把错误结论"诚实地"记下来，**危害不比粉饰小**。

**也别急着怪代码（反向自查）**

`history.append_record` 我一度判定有"表头不一致时静默丢记录"的严重 bug ——
证据链看起来无懈可击，甚至用 `settrace` 逐行追踪确认"没进 `os.rename` 分支"。
**真相：我把 `base_dir` 传成了 `data` 目录**，而 `_path()` 的语义是"项目根目录"，
于是它建了 `data/data/` 把记录写了进去。**代码没撒谎，是我看错了地方。**

> **判断信号**：当一个函数"返回成功"但"看不出效果"时，
> **第一个该怀疑的是自己**：是不是传参语义搞错了？是不是在看另一个文件/目录？
> **写复现脚本前，先读一遍被调函数的参数 docstring。**

### R7 "读不到" ≠ "坏的"：不能因观测失败就付高代价动作 ★

- `client_white_ratio()` 原来把"测不了"（窗口销毁/在屏外/异常）都 `return 1.0`
  → 等价于"判定白屏" → 触发**杀微信重启**（约 40 秒 + 小程序重载全部风险）
- `_hidden` 把跨进程读 Qt `WS_VISIBLE`（不可靠）当依据 → **误判"隐藏到托盘"→ 杀微信**，
  下一行日志就匹配到按钮 `conf=0.999`

**规则**：任何"读不到/测不了/异常"默认按**"没问题"**处理，
让后续**更有信息量的检查**暴露真问题。

### R8 判错方向代价不对称 → 选"宁可暴露问题"那边

- "已通"误判成"没通"：多等一轮
- "被劫持"误判成"已通"：**假成功**，后面全建在错误前提上

→ 凡"成功/失败"判据，**先想清哪个方向错了更贵**，然后往反方向留余量。

### R9 子串匹配是最容易埋雷的判据

`("connected" in stat.lower())` ——
`"connected"` 是 `"disconnected"` 的子串，英文系统下"已断开"被判成"已连接"。

→ 一律**「取字段值 + 白名单精确匹配」，禁止子串 `in`**。
→ 特别警惕 `connected`/`disconnected`、`ok`/`not ok`、`success`/`unsuccessful`
这类"**否定词包含肯定词**"的英文对。
→ **中文因为词形不同（"已连接"/"已断开"）反而没这个问题 —— 所以中文环境下测不出来**，
这是典型的"偶发失败比稳定失败更危险"：**语言一变就静默退化**。

### R10 函数返回值"表达力不足"是隐蔽缺陷类型

`signed_detail_button` 返回 `None` 本身没错，错在**三种情况挤在同一返回值**：

| 情况 | 调用方看到的 |
|---|---|
| (a) 无符合几何的灰块 | `None` |
| (b) 几何像但字迹不像 | `None` |
| (c) **OCR 明确读出「已结束」** | `None` ← **信息被丢弃** |

三者对调用方一模一样 → (c) 被当成"没找到入口" → 判 fail。
**不报错、不告警、不好测。**

> **信号**：函数返回 `None`/`False` 后调用方只能靠"猜"来分支时，
> 就该问 **"是不是丢掉了信息"**。
>
> **修法**：加**可选 `out` 出参**带出事实，**不改返回值**
> （返回值语义常被多处依赖，改它等于让所有调用点重做判断）。

### R11 样本与阈值

- **合成样本不能验证可用性**：合成「已结束」6 档全对 → 判定"没问题"；
  真实样本**立刻暴露 3 个 bug**（倍数上限不够、必须加白边、对边界极敏感）。
  → **合成只验证"逻辑分支"；"到底读不读得出"只能用真实样本。
    真实样本必须写进自动化回归，否则下次改动会静默退化。**
- **验证样本要挑"最可能推翻结论"的那个**，不是最顺手的。
  （真实案例：用干净的那张验证说"防线很稳"，漏掉能证伪的那张
  —— 壁纸填充率 0.40 穿过了 0.35 门槛。）
- **阈值要量正负样本再定，留足余量**：`0.35` 是拍的（0.40 就穿过）；
  `0.55` 是量的（有 37% 缓冲）。

### R12 偶发失败比稳定失败更危险

`test_ocr_real_samples` 用 `scan_buttons` 定位样本按钮（依赖窗口尺寸假设），
跑 2880×1800 历史样本时**连跑 5 次结果不一致**（4 次 0 个、1 次假灰块）。

→ 会让人**习惯性重跑**，最终**连真问题一起忽略**。
→ **测试必须确定性**：改用不依赖环境假设的定位器 + 明确的选择规则。
→ 测试里定位样本按钮要用确定性的 `_find_gray_bar()`，**不要用 `scan_buttons()`**。

### R13 审查必须"先读真实日志，再读代码" ★★

我在同一次复审里**连错三次**，同一个病：
**把"读代码得到的印象"当成"系统实际行为"**（详见 §6.5）。

→ **有真实日志时，先读日志再读代码。**
→ 读日志的价值在于**发现"我没想到的路径"**。
→ **判断历史成败必须读 `logs/signin_*.log`（按天日志）**，不能只看还在的 `run_*` 目录
  —— 早期截图会被清理，但按天日志仍在。**"证据"和"现场"是两份东西。**

### R14 "误报正常状态"与"漏报真故障"是同一枚硬币

**用户痛点**：脚本把"今天还没推送（正常）"报成"签到失败（故障）"
→ 每天产生无意义失败现场 + 飞书告警 + 自愈失败计数。

> **噪音会训练人忽略告警，最终连真故障一起忽略。**

→ **区分"正常状态"与"故障"是核心职责，不是细节。**

## 9. 关键设计决策（不要轻易推翻）

### 9.1 ★ 判成功必须有"界面依据"（AST 测试锁死）

**三路判据取交集**：

| 路 | 作用 | 特点 |
|---|---|---|
| **颜色几何** | 召回（找得到） | 宽松，容易被骗 |
| **字迹风格** | 极性（精度） | 看"底色/对比/墨迹/亮字"特征 |
| **OCR 文字** | **仅否决权** | 有否决权，无确认权之外的权力 |

**OCR veto-only 的核心设计**：

```
读到否定词 → 否决
读到肯定词 → 确认
读不到 / 引擎不可用 / 任何异常 → 放行
```

> **第三条最重要**：读不到是常态，若当否决，**脚本会在最需要它时集体摆烂**。

**理由**：认错方向不利 —— 已结束 → 已签到 = **假成功**。

### 9.2 OCR 实现细节

| 项 | 决定 | 理由 |
|---|---|---|
| 依赖包 | 分体式 `winrt-*`（约 2.9MB） | **绝不用 `winsdk`** —— 便携 Python 上编译失败 |
| 多倍数重试 | `scales=(10, 8, 6, 12, 4, 5, 3, 2)` | **10x 排第一** —— 漏读「已结束」= 假成功代价最大 |
| 预处理 | **必须先 Otsu 二值化**（`_ocr_binarize`） | 这是「已结束」能读出的**前提** |
| 双路径 | `preprocess=("otsu","raw")` | otsu 优先，raw 保留 |
| 裁图 | 必须过 `_ocr_pad_to_canvas` | 四周留按钮高 **22%** 白边 |
| 文本匹配 | **全文匹配优先于残缺片段** | 低倍数会读出 `'已'`/`'已纟'`/`'已签至刂'`，既不是「已签到」也不是「已结束」，拿去否决 = **瞎猜**。逻辑：**先找完整词，整轮找不到才退回最长的片段** |
| 截图 | 过程 JPEG q75，失败现场 PNG | 保分辨率、只换编码最优 |

### 9.3 ★ 中断兜底：`atexit` 救不了强杀

见 §4 Q6。**三层必须保留，不要把 ③ 简化掉。**

### 9.4 微信有两个标题不同的顶层窗口

```
标题='微信'    cls=Qt51514QWindowIcon  rect=(4,0,1122,1715)      1118x1715  ← 主界面
标题='Weixin'  cls=Qt51514QWindowIcon  rect=(1267,634,1613,1025)   346x391  ← 登录/托盘窗
```

`find_wins("微信", exact=True)` **只认标题恰为「微信」的那个**。
承载「进入微信」按钮的窗口标题**可能是「微信」也可能「Weixin」**
（取决于当前阶段）。**别假设"标题=微信"的就该操作。**

### 9.5 窗口宽度必须每次纠正（`_normalize_wechat_size`）

见 §4 Q3。**关键：只在超标时才缩到 1118×1715；本来 <=1400 就一个像素都不动**（保留而非替换）。

### 9.6 盲点越界坐标必须拒绝（P0-1 系列）

`match()` 不传 roi → 整屏搜索 → 命中**另一个窗口**的按钮，越界 308px，照样点 → 不生效。

**修**：`match(..., must_be_in=(x1,y1,x2,y2))`，
命中点不在矩形内 → `(-1.0, None, None)` + warning。

> **为什么不用"改成传 roi"**：传 roi 会**改变匹配行为**（属改变功能，风险高）；
> 几何校验只把"明显不可能"的降级，**不改变能找到的情况**。
>
> ★ **注意**：`must_be_in` 会**罚分压低 conf**，
> 所以**日志里的低 conf 不代表阈值失效**（见 §8 R5、§6.6 最后一行）。

### 9.7 点击类动作必须验证"界面有没有变"（P0-2 系列）

`step_enter_wechat` 点击后只调 `wait_wechat_rendered()`，而它**只判白屏** →
登录页不是白屏 → 立刻返回"已就绪" → **完全失去"发现没进去"的能力** → 反复杀微信重启。

**修**：点击后**再匹配一次那个按钮**，仍在 → `logger.error` + 存 `FAIL_*` + `return False`；
**不重启微信，失败干脆暴露。**

> **判据必须针对这个动作的预期结果。**
>
> **复核要"多轮重试、任一次确认按钮消失即放行"**
> （只查一次会把"点击成功但按钮在淡出"误判为失败 —— **假失败比漏判更糟**）。

### 9.8 门户劫持判定必须"查最终 URL + 查特征串"

见 §4 Q19。

### 9.9 `unknown` 与 `fail` 要分开

`_run_outcome()` 原把 `unknown` 归入失败保留期（90 天）→ 让"读不出结果"的目录占盘。
现用 `KEEP_UNKNOWN_DAYS`(14) 单独处理。

**退出码语义**：`success=0` / `fail=1` / **`not_time=3`（"并非失败"）**。

### 9.10 ★ 通知必须是"旁路"，绝不能影响主流程

| 决定 | 理由 |
|---|---|
| 通知模块**只返回 `True`/`False`，绝不抛异常** | 通知是旁路。**发不出去也不能让签到失败** |
| 所有调用点包 `try/except`，失败只 `logger.warning` | 同上。09-16 16:35/16:36 两次网络故障即实证（§2.12） |
| 用**纯标准库** `urllib`，不用 `requests` | 保住"**拷贝即用**"核心特性（便携 Python 不装第三方包） |
| 通知**只报告**结果，**不参与判定** | 判据仍是§9.1 的三路取交集，通知无权改判 |
| 读的是**落盘事实**（`result.txt` / `step_trace.json`） | 不靠内存变量 —— 内存变量在异常路径下可能没写到（§8 R5） |
| **一次运行只推一条结果**（`_FEISHU_DONE` 幂等） | 异常路径可能让同一次运行走到多个调用点 → 会推两遍 |
| **`not_time` 用橙色，不用红色** | 直接体现"**正常状态 ≠ 故障**"（§8 R14）—— 红色会训练用户忽略告警 |
| **连续失败才升级红色** | 且**只在"本次也失败"时升级** —— 成功不会被历史拖累 |
| **读不到台账就返回 `False`**（不升级） | **宁可少告警，也不因统计模块出问题而误报** |

> ★ 这一条与§9.1（判成功必须有界面依据）是一对：
> **§9.1 管"别把失败说成成功"，§9.10 管"别让通知反过来搞坏签到"。**

## 10. ★ 维护约定（给所有 agent 的硬性要求）

> **本节是强制性约定，不是建议。任何 agent 接手本项目，都必须遵守。**

### 10.1 一切修复必须走"可插拔形式"

**禁止**直接手工编辑 `signin.py` 来做修复。

**必须**：

1. 在 `补丁包/patches/` 下新建或修改补丁定义（JSON）
2. 用 `补丁包/patch_engine.py` 的 `check` 校验能否安装
3. `apply` 安装 → 跑 `smoke_test.py` 确认 158 项全过
4. 需要回退就 `revert`（引擎保证**逐字节还原**）

**理由**：

- `signin.py` 是跑了很久的稳定主干，**直接改 = 承担不可逆风险**
- 补丁形式**天然可回退**，且回退有 sha256 证明
- 补丁定义**自带锚点校验**，改错位置会被拦住
- 用户明确要求："这样就不会影响主程序，如果装上去发现有问题还可以拆下来完善后继续装上去用"

**例外**：仅当修复无法用补丁表达（**大范围重构**）时，才允许直接改主干。
此时必须：① 改前存基线 + sha256 ② 改后跑全量测试 ③ **在本文档 §4/§6 追加记录**。

### 10.2 每次修复必须配负向测试

**没有负向测试的护栏 = 摆设。**

按 §8 R3/R4 执行：

- 先固定干净基线 + 记录 sha256
- 故意改坏被守护的代码，**确认断言 FAIL**
- 每个子检查**逐个验，不许抽查**
- 裁决必须是 `REAL`，`DUMMY`/`BLIND`/`SKIP` 一律**不算通过**
- **负向测试脚本必须内建"每条用例前恢复基线"**（防假 REAL）

### 10.3 测试通过与一致性确认

```bash
./runtime/python.exe smoke_test.py         # 158 项全过
```

- **连跑 3~8 次确认结果一致**（防偶发失败）
- 新增测试函数**不会自动注册** —— 必须在 `main()` 里手动加一行调用
  （`smoke_test.py` 末尾附近；**本次踩过：加了断言但数字没变**）
- **验证后必须核对真实日志行数 / run 目录没变**（`wc -l` + `ls -dt logs/run_*`）

### 10.4 ★★ 每次修改完成后，必须同步更新本 README

**这是硬性要求。** 更新什么：

| 场景 | 必须更新 |
|---|---|

## 13. 环境与工具约定

### 13.1 运行环境

| 项 | 约定 |
|---|---|
| **跑脚本/量图片** | **必须用 `runtime/python.exe`**（系统 Python 没装 PIL/cv2） |
| **中文路径 `cv2.imwrite`** | **静默失败**（返回 False 不抛异常）→ 用 `cv2.imencode(...).tofile()` |
| **读图** | `cv2.imdecode(np.fromfile(path, dtype=np.uint8), cv2.IMREAD_COLOR)` |
| **GUI 自动化** | 该沙箱**跑不了**（登录态问题）→ 全部用离线/静态验证 |
| **PowerShell 工具** | 在此环境**基本无回显**，且禁止调 `cmd.exe` → **全程 Bash + Python** |
| **Bash 里 `cmd //c xxx.bat`** | 会进交互模式不执行，**别用** |
| **`schtasks.exe`** | 沙箱禁用 → 测 `.bat` 逻辑用 **Python 等价复刻语义** |
| **`.bat` 编码** | 含中文的必须 **GBK 正文 + `chcp 936`**（曾因 UTF-8 正文乱码） |
| **回收站 API** | 在此沙箱被拦（`Add-Type`、`Shell.Application` COM 都被拒，`gio`/`trash-put` 不存在）→ **删除目录只能请用户手动做**，不要绕过安全策略 |

### 13.2 ★ 临时目录一律 `tempfile.mkdtemp()`

**绝不用 `os.path.abspath(".")` / `os.getcwd()`**

> **原因**：后者取决于"**从哪启动**"，与"脚本放哪"无关。
>
> **2026-09-16 踩过**：算成 `D:\`，把测试日志写到了 D 盘根目录 `D:\_tmp_probe_logs`。

### 13.3 测试环境隔离

**需 import `signin` 时，必须先设**：

```bash
SIGNIN_LOG_DIR_OVERRIDE=<临时目录>
```

> 否则噪音会写进**真实按天日志**，而按天日志是排查故障的**一级依据**。

### 13.4 文件读写

- **按字节读写**（`rb` / `wb`）+ 显式换行 —— 文本模式会**静默**把 CRLF 转 LF
- **原子写盘**：临时文件 + `os.replace`（进程中断不会留半截文件）
- 中文路径相关操作一律走 `encode`/`tofile` 路线

## 附：一句话总结

> **这个项目的核心不是"能自动签到"，而是"能诚实地告诉你它有没有签到"。**
>
> 为此我们付出了：一次假成功事故、一次反向误判、一次语义错误、
> 三次静态推断被真实日志推翻、五次"字符串断言"翻车、
> 以及一套可插拔的修复机制 —— 让每一次改动都**可验证、可回退、可追溯**。
>
> **判成功必须有界面依据。失败必须暴露。修复必须可插拔。**
> **改完必须更新本文档。**
