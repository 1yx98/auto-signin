# 僵尸窗口过滤补丁包 —— 可插拔修复 Z

> 建于 2026-09-17。**修的是 09-17 那次「签不上 + 任务栏反复弹窗」的根因。**

## 这个包修的是什么

**症状**：脚本在「进入微信」阶段失败，搜索框匹配不上（conf 0.32~0.49），
然后**反复重启微信** —— 用户看到**任务栏反复弹窗**。

**真根因：僵尸窗口（zombie window）**

微信退出/崩溃后，它的**顶层窗口对象会在系统里残留**：
可以枚举、`GetWindowRect` 仍返回有效坐标（看起来完全正常），
但 `IsWindowVisible` 恒为 0，且**任何激活手段都无效** —— 因为进程已经死了，
没有任何人处理窗口消息。

```
微信退出 → 主界面窗口（1118x1715）残留为僵尸
  → find_wins("微信") 找到它（rect 大，按面积排序排第一）
  → activate() 选中它 → ShowWindow/SetForegroundWindow 全无效
  → 真正可用的窗口（登录页 586x773）从未被激活
  → 点击落空 → 搜索框匹配失败 → 重启微信
  → 僵尸仍在枚举列表里 → 死循环 → 任务栏反复弹窗
```

**2026-09-17 的实测铁证**（两个窗口尺寸完全不同，证明是两个窗口）：

| | 脚本看到的 | 真实可用的 |
|---|---|---|
| hwnd | 393430 | 655858 |
| rect | (879,0,1997,1715) | **(1147,472,1733,1245)** |
| 尺寸 | 1118x1715（**已登录时的主界面尺寸**） | **586x773（未登录时的登录页尺寸）** |
| 状态 | `Visible=0`（僵尸） | `Visible=1` |

> 586x773 正是 `README` 里记的 09-07~09-15 那 8 次成功运行的窗口尺寸。

## 怎么修

| id | 做什么 |
|---|---|
| Z1 | 注入 `_win_is_zombie()` —— 用 `OpenProcess` + `GetExitCodeProcess != STILL_ACTIVE` 判断"拥有它的进程还活着吗" |
| Z2 | `find_wins()` 在**进入候选列表之前**过滤掉僵尸窗口 |

**为什么必须在"进候选列表前"过滤**：僵尸窗口 rect 大，在 `activate()` 的
`prefer_largest` 排序里总是排第一，选中它就必然失败。

**★ 安全设计**：`_win_is_zombie()` **取不到信息时一律按"活着"处理**（返回 False）。
这是本项目铁律「**读不到 ≠ 坏的**」—— 宁可留下一个可疑窗口，
也绝不因为权限问题把正常窗口误判成僵尸而丢掉它。

## ★ 本包在补丁链中的位置

本包**不是**第一个包。当前共 5 个包改同一个 `signin.py`，基线逐层叠加：

```
补丁包             基线 af386517（原版）        → P1a+P1b → 2f2d675c
跳过无效滚动补丁包   基线 2f2d675c（装了P1）      → P2a+P2b → ed1f161e
僵尸窗口过滤补丁包   基线 ed1f161e（装了P1+P2）   → Z1+Z2   → 5965e9df   ← 本包
进程检测补丁包       基线 5965e9df（装了P1+P2+Z） → P1+P2   → 17ea5522
进入微信判定补丁包   基线 17ea5522（再装P）       → E1      → 548668b2
```

**所以本包不能单独拆卸**（拆它会连带把 P1/P2 一起带走）。

**正确的拆卸顺序**（从后往前，不能颠倒）：
```
进入微信判定补丁包  revert E1
进程检测补丁包      revert P2 → revert P1
僵尸窗口过滤补丁包  revert Z2 → revert Z1
跳过无效滚动补丁包  revert P2b → revert P2a
补丁包              revert
```

顺序颠倒会被**跨包防护**拦住（这是设计，不是故障）——原则：**宁可拆不掉，不可拆错**。

## 已知边界

- 本包**只能阻止**脚本选中僵尸窗口，**不能**让微信不产生僵尸窗口。
  僵尸窗口的**来源**（微信未登录时自行退出）属于微信自身行为，脚本管不了。
- `_win_is_zombie()` 每次 `find_wins` 都会对候选窗口调一次 `OpenProcess`
  —— 开销极小（微秒级，且不启动子进程）。

## ★★ 2026-09-18 修正：`_win_is_zombie()` 原来**判不出僵尸**（真 bug）

**用真实数据离线验证时发现的**（不是猜的）：

```
对一个刚被杀掉的 pid 调 OpenProcess(0x1000) -> 失败, GetLastError = 87
  87 = ERROR_INVALID_PARAMETER -> 该 pid 不存在（进程已退出）
```

而**僵尸窗口的定义恰恰就是「拥有它的进程已经死了」**。
原来那句「打不开 -> 不敢断言 -> 按活着处理（`return False`）」
**把死进程也一并当成了活着的** —— 于是僵尸永远判不出来，**整个 Z 补丁等于失效**。

**修法**：按错误码区分 ——
```python
if not _h:
    _err = kernel32.GetLastError()
    if _err == 87:      # 该 pid 不存在 -> 进程已退出 -> 僵尸
        return True
    return False        # 其它（如 5=权限不足）-> 不敢断言 -> 按活着处理
```
**铁律 R7（读不到 != 坏的）仍然保住**：只有「明确读到 87」才判僵尸，
其它失败原因一律按活着处理。

**修后验证**：活窗口 **0 误判**（安全底线保住）；
「真僵尸 -> True」那一侧仍需等真实场景（微信退出后残留窗口）才能最终确认。
